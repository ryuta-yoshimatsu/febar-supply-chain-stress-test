# Decisions and trade-offs

| # | Decision | Alternatives considered | Why this choice | What we give up |
|---|---|---|---|---|
| 1 | **Mathematical optimization (Pyomo + HiGHS LP/MIP) is the source of truth for impact**; the LLM only routes, explains and recommends | Let the LLM reason about impact; Monte-Carlo simulation; rules of thumb (weeks of cover) | Optimal re-planning gives the *unavoidable* loss after the best response, is fully explainable (every shifted unit is a decision variable) and is deterministic, so the agent cannot hallucinate impact numbers | Needs a well-specified network model; linear assumptions (no lead-time dynamics, unit BOM coefficients) |
| 2 | **Time-to-recover (TTR) / time-to-survive (TTS) formulation** (Simchi-Levi et al.) | Single "risk score" per supplier | Two numbers planners already understand: how long a supplier is down vs. how long we can cope. The gap is directly actionable | TTS is unbounded when alternates fully cover a loss; we **cap TTS at a 52-week planning horizon** (52 = "survives the year"), otherwise the solver returns a degenerate answer |
| 3 | **HiGHS** (open source) | Gurobi / CPLEX | No licence, runs on serverless, solves 28 scenarios × 3 models in ~1.4 s at this size (measured) | Commercial solvers are faster on very large networks; swap-in is a one-line change in Pyomo |
| 4 | **Lakeflow Declarative Pipeline (SQL) with Auto Loader** for ingestion | Notebook ETL, Lakeflow Connect to a real ERP | Incremental file ingestion, declarative data-quality expectations, lineage and retries for free. SQL keeps it reviewable by data engineers | Synthetic files stand in for real connectors; in production the bronze layer would come from Lakeflow Connect (SAP, Salesforce, etc.) |
| 5 | **Gold tables as materialized views; stress-test outputs as Delta tables written by a job** | Run the optimizer inside the pipeline | The optimizer is Python + a solver with its own retry/scale profile; keeping it in a job task keeps the pipeline pure SQL and lets the stress test scale out (Ray) independently | Two orchestration units (pipeline + notebook) instead of one; both live in one Databricks Job |
| 6 | **Lakebase synced tables (snapshot) for serving**, Postgres `app_state` schema for app writes | Query Delta through a SQL warehouse from the app | Millisecond lookups and transactional writes (scenario log, chat history) without keeping a warehouse warm; still governed via Unity Catalog | Snapshot sync is refreshed by the job, not continuous. Continuous/triggered sync would need CDF on all sources and costs more |
| 7 | **Agent runs inside the Databricks App** (LangGraph + `databricks-claude-sonnet-5-5`), and is also logged, evaluated and registered in UC with MLflow | Model Serving endpoint + app as thin client | One deployable, ~1.5 min builds, no PATs (the app service principal authenticates everything), and the agent tools reuse the app's Lakebase connection | No Model Serving inference tables / review app; we compensate with MLflow tracing, `mlflow.genai.evaluate` and a registered model version, and the same package can be deployed with `agents.deploy` later |
| 8 | **Genie as an agent tool** for descriptive analytics, optimizer for what-ifs | Hand-written SQL tools for every question; Genie only as a separate UI | Planners ask open-ended questions ("which products are single-sourced for sweetener?"); Genie covers the long tail with governed SQL while the agent keeps what-ifs on the optimizer | Genie adds latency (~10-20 s) and the space needs curated instructions and example SQL |
| 9 | **App service principal auth (not on-behalf-of-user)** | OBO user tokens | Business users do not need direct grants on tables, Genie or the LLM; least privilege is enforced once on the SP (gold-only SELECT, CAN_RUN on Genie, CAN_QUERY on the LLM) | Row-level personalisation by user is not applied; user identity is still recorded in the scenario log and chat history |
| 10 | **Hand-designed synthetic network with seeded quantities** | Random topology from the original accelerator; public datasets | The story needs realistic CPG exposure (single-sourced seasoning, one PET bottle line for two brands, shared sweetener base). No public dataset has multi-tier BOM + capacity + inventory | Not a real company; numbers are illustrative but internally consistent |
| 11 | **Injected data-quality defects** (duplicate supplier, negative inventory scan, link to unknown supplier) | Clean synthetic data | Shows the pipeline's expectations doing real work and keeps bad rows out of the optimizer | none |
| 12 | **Pinned, fully-resolved app dependencies** | Loose `requirements.txt` | Unpinned resolution made the first app build backtrack for >10 minutes and time out; pinned builds take ~90 s | Manual upgrades |
